# UI-компоненты

## Обязательные артефакты

Для каждого нового UI-компонента, а также при изменении его публичного API или
поведения, обязательно:

- создать или обновить тесты рядом с компонентом: `component-name.test.tsx`;
- создать или обновить Ladle-истории рядом с компонентом: `component-name.stories.tsx`;
- не считать задачу завершённой, пока релевантные тесты, типы и линтер не проходят.

Исключение возможно только по прямому указанию пользователя. Если тест или story
невозможно добавить, объясни причину в итоговом сообщении.

## Соглашения об именовании и структуре

- Имена файлов — в нижнем регистре (`button.tsx`, `button.stories.tsx`,
  `button.test.tsx`), само имя компонента — в `PascalCase` (`Button`).
- Компонент, его стили, тесты, story и `index.ts` живут в одной папке
  (`src/shared/ui/<component>/`).
- Публичный API компонента экспортируется через `index.ts`; наружу компонент
  доступен из общего API `@/shared/ui`. Внутренние файлы напрямую не импортируются.
- Переиспользуемые UI-примитивы — в `src/shared/ui`; компоненты, привязанные к
  предметной области, — в соответствующем домене (`src/domains/<domain>`).

## Требования к тестам

- Тестируй поведение, доступное пользователю, а не внутреннюю реализацию.
- Используй запросы по роли, доступному имени и тексту; взаимодействуй через
  `userEvent` (`@testing-library/user-event`).
- Покрывай основной сценарий и все значимые состояния: `loading`, `error`,
  `empty`, `disabled`, выбранное состояние и обработку пользовательских действий.
- Проверяй базовую доступность: семантические элементы, доступные имена, работу
  с клавиатурой и видимый фокус, когда это применимо.
- Тесты пишутся на русском языке (`describe`/`it`), как и остальные в проекте.
- Не добавляй snapshot-тесты без конкретной причины.

## Требования к Ladle-историям

- Добавляй story для состояния по умолчанию и всех значимых визуальных состояний.
- Используй `args` и `argTypes` (controls) для публичных props.
- Именуй экспорты историй в `PascalCase`; задавай `title` в `StoryDefault`
  по пути домена (например, `shared/ui/Button`).
- Используй реалистичные, но локальные данные; stories не должны зависеть от сети,
  API или случайных данных.
- Для интерактивных компонентов добавляй `play`-сценарии, если это уместно.
- Story должна быть понятной демонстрацией компонента для ручной проверки.
- Учитывай тёмный/светлый фон каталога (addon `background` в `.ladle/config.mjs`),
  если компонент зависит от фона.

## Качество компонентов

- Следуй существующим паттернам, дизайн-системе и структуре ближайших компонентов.
- Не добавляй новую UI-библиотеку или новую зависимость без необходимости и явного
  согласования.
- Используй семантический HTML, токены дизайн-системы (`src/shared/styles/tokens.css`)
  и существующие базовые компоненты (`Icon` и т.п.).
- Стили — через `*.module.scss` (CSS Modules); переиспользуемую типографику бери из
  SCSS-миксинов (`src/shared/styles/_mixins.scss`). Не хардкодь цвета и шрифты —
  используй CSS-переменные из токенов.
- Props должны быть типизированы; избегай `any` и неявных контрактов.
- Не смешивай получение данных, сложную бизнес-логику и отображение в одном
  компоненте, если это ухудшает читаемость или повторное использование.
- Учитывай адаптивность, пустые состояния и локализацию, если это релевантно
  интерфейсу.

## Проверка перед завершением

Выполни относящиеся к изменению проверки и исправь ошибки, вызванные своей работой:

- `npm run test:run`
- `npm run lint`
- `npm run lint:styles`
- `npm run typecheck`
- `npm run ladle:build` (сборка каталога Ladle)

Полный прогон всех проверок разом — `npm run quality`.
